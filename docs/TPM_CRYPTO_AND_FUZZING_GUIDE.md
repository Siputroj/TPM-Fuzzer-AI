# Comprehensive Guide: TPM 2.0 Cryptography, Execution Workflows, & Cryptographically-Aware Fuzzing

> **Purpose:** This document breaks down how TPM 2.0 handles keys and sessions, traces the exact wire input/output lifecycle, details what the previous team implemented in `src/harness/session_auth.cc`, why it still hits coverage walls, and provides a step-by-step roadmap for achieving deep cryptographically-aware fuzzing.

---

## 1. Core Concepts: Keys, Sessions, & Authentication in TPM 2.0

### Does the TPM give you an all-purpose key to validate commands?
**No.** The TPM does not hand out a universal "master key" or API token. 

Instead, TPM 2.0 security relies on two distinct mechanisms:
1. **Entities & Authorization Values (`authValue`):** Every object inside the TPM (hierarchies, keys, NV indices, PCRs) has an owner and an optional secret password (`authValue`). By default on initialization, these are empty (0-length byte arrays `""`).
2. **Authorization Sessions:** To perform operations on protected entities without sending raw passwords in cleartext over the bus, the caller establishes a temporary **Session**.

---

### Key Creation vs. Session Creation

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 1. KEY CREATION (TPM2_CreatePrimary)                                                   │
│    • Caller sends template (RSA 2048, ECC, etc.) to a hierarchy (e.g., Owner 0x40000001)│
│    • TPM derives the key deterministically from internal Primary Seeds in hardware.    │
│    • TPM loads the key into volatile RAM and returns:                                  │
│        - Handle (e.g., 0x80000000)                                                     │
│        - Public Key parameters                                                         │
│        - TPM Name (Cryptographic Hash of public parameters: AlgID || Hash(Public))      │
└────────────────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 2. SESSION ESTABLISHMENT (TPM2_StartAuthSession)                                       │
│    • Caller asks TPM to start a session (HMAC session or Policy session).              │
│    • Caller supplies a starting random nonce (nonceCaller).                            │
│    • TPM creates a session slot in internal memory and returns:                        │
│        - sessionHandle (e.g., 0x02000000)                                              │
│        - nonceTPM (Random bytes generated by TPM hardware DRBG)                        │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

## 2. End-to-End Execution Workflow: Input to Output

Every single TPM 2.0 command follows a strict request-response lifecycle across the wire.

```text
┌─────────────────────────┐               ┌──────────────────────────────┐               ┌─────────────────────────────┐
│     CALLER / FUZZER     │               │     TPM WIRE & AUTH GATE     │               │    TPM CORE & EXECUTION     │
│    (src/harness/)       │               │ (ExecCommand / SessionProc)  │               │    (command/ & subsystem/)  │
└───────────┬─────────────┘               └──────────────┬───────────────┘               └──────────────┬──────────────┘
            │                                            │                                              │
  [ Phase 1: Preparation ]                               │                                              │
  • Prepare handles & parameters                         │                                              │
  • cpHash = Hash(CC || Names || Params)                 │                                              │
  • HMAC = HMAC(sessionKey, cpHash || nonces)            │                                              │
  • Pack 4-segment wire buffer                           │                                              │
            │                                            │                                              │
            │ ── 1. Deliver Wire Packet [Tag|Size|CC] ─► │                                              │
            │                                            │                                              │
            │                                  [ Phase 2: Auth Gate ]                                   │
            │                                  • Verify 10-byte header                                  │
            │                                  • Resolve entity handles in RAM                          │
            │                                  • Recompute cpHash using Names                           │
            │                                  • Check caller HMAC == expected                          │
            │                                    (If mismatch -> Return TPM_RC_AUTH_FAIL)               │
            │                                            │                                              │
            │                                            │ ──── 2. Dispatch to Target Handler ────────► │
            │                                            │                                              │
            │                                            │                                    [ Phase 3: Core Run ]
            │                                            │                                    • Unmarshal params
            │                                            │                                    • Execute TPM2_<Cmd>()
            │                                            │                                    • State/NVRAM updates
            │                                            │                                              │
            │                                            │ ◄─── 3. Return Execution Results ─────────── │
            │                                            │                                              │
            │                                  [ Phase 4: Response & Nonce Roll ]                       │
            │                                  • DRBG: nonceTPM = NEW_RANDOM()                          │
            │                                  • Build Response Header & HMAC                           │
            │                                            │                                              │
            │ ◄─ 4. Deliver Wire Response Buffer ─────── │                                              │
            │                                                                                           │
  [ Phase 5: Feedback for Next Command ]                                                                │
  • Unpack Response [Tag | Size | RC | Params]                                                          │
  • Extract updated nonceTPM from auth area                                                             │
  • Use updated nonceTPM for Command #2 in sequence!                                                    │
            │                                                                                           │
```

### Detailed Breakdown of the Steps

#### Step 1: Caller Prepares the Wire Packet
The packet has 4 mandatory segments:
```text
[ Wire Header (10B) ] [ Handle Area ] [ Authorization Area ] [ Parameter Area ]
```
* **Wire Header (10B):**
  * `tag` (2B): `0x8001` (`TPM_ST_NO_SESSIONS`) or `0x8002` (`TPM_ST_SESSIONS`).
  * `commandSize` (4B): Total length in big-endian bytes.
  * `commandCode` (4B): E.g., `0x00000153` for `TPM2_Create`.
* **Handle Area:** 32-bit handle values referencing keys or hierarchies (e.g. `0x80000000`).
* **Authorization Area:**
  * `authSize` (4B): Size of authorization structures.
  * `sessionHandle` (4B): E.g. `0x02000000`.
  * `nonceCaller` (TPM2B): Fresh 16–32 random bytes from caller.
  * `sessionAttributes` (1B): Bitmask (`continueSession`, `decrypt`, `encrypt`).
  * `hmac` (TPM2B): 32-byte SHA-256 HMAC signature.
* **Parameter Area (`cpBuffer`):** Command-specific arguments (key sizes, attributes, data blobs).

#### Step 2: The Authorization Calculation
To compute the HMAC before sending:
1. **Command Parameter Hash (`cpHash`):**
   $$\text{cpHash} = \text{Hash}(\text{commandCode} \parallel \text{Name}(h_1) \parallel \dots \parallel \text{Name}(h_n) \parallel \text{Parameter Area})$$
   *(Note: The Name of a handle is its unique cryptographic identity. For a key, $\text{Name} = \text{AlgID} \parallel \text{Hash}(\text{publicArea})$).*
2. **Session HMAC:**
   $$\text{HMAC} = \text{HMAC}(\text{sessionKey} \parallel \text{authValue}, \text{cpHash} \parallel \text{nonceCaller} \parallel \text{nonceTPM} \parallel \text{sessionAttributes})$$

#### Step 3: TPM Validation & Execution
* The TPM unmarshals the packet, reads the handles, retrieves their Names from internal tables, and independently computes `cpHash`.
* The TPM compares its calculated HMAC with the HMAC in your packet.
* If identical, it passes execution to the target handler (e.g., `TPM2_Create`).

#### Step 4: Output & Nonce Invalidation (Critical!)
* When the TPM returns a response, **it always generates a brand new `nonceTPM`** and includes it in the response authorization area.
* **In a chain of commands:** For Command #2, the caller **must discard the old `nonceTPM`** and use the new `nonceTPM` received in Response #1. If it fails to do so, Command #2 is immediately rejected with `TPM_RC_BAD_AUTH`.

## 3. What the Previous Team Implemented

The previous team recognized that raw LibFuzzer could never guess a 256-bit HMAC, so they wrote [`src/harness/session_auth.cc`](file:///Users/siputroj/Desktop/TPM-Fuzzer-AI/src/harness/session_auth.cc):

1. **Session Snooping (`CaptureStartAuthSessionCommand`):**
   * Sniffs outgoing `TPM2_StartAuthSession` commands.
   * Intercepts the response in `SessionAuthProcessResponse` to save `g_session.handle` and `g_session.nonce_tpm`.
2. **Name Tracking Table (`NameTable`):**
   * Stores up to 16 mappings of `handle -> Name`.
   * Intercepts responses from `TPM2_CreatePrimary` and `TPM2_Load` to parse out and save the new key's cryptographic Name.
3. **Pre-Flight Wire Patching (`SessionAuthPatchCommand`):**
   * Looks up handles in `command_attributes.h`.
   * Dynamically calculates `cpHash = SHA256(commandCode || Names || params)`.
   * Calculates `HMAC_SHA256` using OpenSSL.
   * Overwrites the dummy HMAC bytes inside the buffer right before calling `_plat__RunCommand()`.
4. **Post-Flight Feedback (`SessionAuthProcessResponse`):**
   * Extracts the updated `nonceTPM` from the response wire buffer and saves it for the next command in the loop.

## 4. What Was Missed & Why Coverage Still Hits a Ceiling

While the previous team's solution was a huge step forward, it was a **minimal prototype** with major architectural gaps that cause deep fuzzing to fail:

| Limitation | Where in Code | Why It Fails & Causes Coverage Ceiling |

If the fuzzer mutates `tpm_key` or `bind` to use real encryption/binding, the harness disables itself, causing instant `TPM_RC_AUTH_FAIL`. |
| **2. TPM 2.0's entire Enhanced Authorization subsystem (`command/EA/`: `PolicyPCR`, `PolicySecret`, `PolicySigned`, `PolicyAuthorize`) requires Policy sessions, which track a cumulative `policyDigest`. These code paths are 100% unreached. |
| **3. Hardcoded SHA-256 Everywhere** | [`session_auth.cc:L322`](file:///Users/siputroj/Desktop/TPM-Fuzzer-AI/src/harness/session_auth.cc#L322) | `ComputeCpHash` hardcodes `SHA256_CTX` and 32-byte buffers. ## 5. Concrete Roadmap to Cryptographically-Aware Fuzzing

To reach full code coverage in `vendor/TPM`, we implement the following 4 milestones:

### Milestone 1: Complete Command Table & Name Extractors (Immediate Win)
1. Add all 24+ active TPM commands into `include/harness/command_attributes.h` (specifying exact `handle_count`, `auth_handle_count`, and `out_handle_count`).
2. Add Name extractors in `session_auth.cc`:
   * `ExtractNVName`: For `TPM2_NV_DefineSpace`, computes $\text{Name} = \text{HashAlg} \parallel \text{Hash}(\text{nvPublic})$.
   * `ExtractContextLoadName`: Restores Names when handles are restored from saved context blobs.

### Milestone 2: Generalized OpenSSL EVP Digest Architecture
Replace all hardcoded `SHA256_*` calls in `session_auth.cc` with OpenSSL EVP:
```cpp
const EVP_MD* md = GetEVPForTPMAlg(g_session.hash_alg); // Supports SHA1, SHA256, SHA384, SHA512
EVP_MD_CTX* ctx = EVP_MD_CTX_new();
EVP_DigestInit_ex(ctx, md, NULL);
// update and finalize dynamically according to EVP_MD_size(md)
```

### Milestone 3: Salted & Bound Session Key Derivation (`KDFa`)
Support `tpm_key != TPM2_RH_NULL`:
1. When starting an auth session with an asymmetric key, extract the encrypted salt.
2. In the harness, compute the shared secret using the private key.
3. Implement `KDFa()` (TPM 2.0 Part 1 §21) in the harness:
   $$\text{sessionKey} = \text{KDFa}(\text{authHash}, \text{sharedSecret}, \text{"ATH"}, \text{nonceTPM}, \text{nonceCaller}, \text{bits})$$
4. Use this computed `sessionKey` in `HMAC` calculations rather than an empty key.

### Milestone 4: Policy Session Engine (`TPM2_SE_POLICY`)
1. Extend `SessionState` to track `policy_digest`.
2. When `session_type == TPM2_SE_POLICY`:
   * On session start: `policy_digest = 0x00...00`.
   * When `TPM2_PolicyPCR` is sent: update `policy_digest = Hash(policy_digest || TPM_CC_PolicyPCR || pcrSelection || pcrDigest)`.
   * When `TPM2_PolicyCommandCode` is sent: update `policy_digest = Hash(policy_digest || TPM_CC_PolicyCommandCode || code)`.
3. When the guarded command is dispatched, the policy digest will match the TPM's internal policy assertion, penetrating the entire `command/EA/` directory.
